# 3 РЕАЛИЗАЦИЯ НА ДЖАВЕ И ОРГАНИЗАЦИОННЫЙ РАЗДЕЛ

## 3.1 Диаграмма классов

В объектной модели сохранены все десять сущностей из раздела 2.2. Заявитель соответствует Applicant, заявка — Application, документ — Document, связь между заявкой и документом — ApplicationDocument, согласие — Consent, результат проверки — CheckResult, доход — Income, обязательство — Obligation, решение — Decision, попытка уведомления — Notification. Наследники Approval и Refusal уточняют общую сущность решения. На диаграмме (рисунок 3.1) использованы обозначения UML 2.5.1 [25].

![Рисунок 3.1 — Диаграмма классов прототипа рассмотрения заявки](models/classes.png)

Один заявитель связан с нулём или несколькими заявками, доходами и обязательствами. Документы могут фигурировать в нескольких заявках через ApplicationDocument. С заявкой может быть связано одно итоговое решение, а с решением — несколько попыток уведомления. В памяти эти ссылки выражены идентификаторами из JSON. Наследование связывает Decision с Approval и Refusal. Стрелки реализации связывают CompletenessRule с RequiredField и RequiredDocument. Композиция показывает, что ReviewWorkflow создаёт и хранит собственные объекты проверки комплектности и расчёта нагрузки.

## 3.2 Объектно-ориентированная реализация

Исходники размещены в src/java. Для сборки используются Maven и целевая версия Java 21. Main читает аргумент --data, JsonCases преобразует JSON в предметные объекты и сериализует результат, а ReviewWorkflow выполняет сценарий. Такое разделение позволяет менять способ чтения и записи данных без переноса предметных правил в консольный интерфейс [27]. Данные синтетические, обрабатываются в памяти. Итоговое одобрение или отказ поступает из записи сотрудника во входном файле.

Записи Java хранят компоненты в закрытых полях и дают доступ через методы. В Decision и Approval поля объявлены закрытыми явно. Иерархия типов и реализация интерфейса опираются на правила Java SE 21 [26]. Approval проверяет положительные сумму и срок, Refusal требует основания и не хранит одобренные условия. Оба типа реализуют контракт Decision и наследуют от него запись уведомления.

Фрагмент 3.1 — Выбор конкретного решения в Application.recordDecision

```java
Decision decision = switch (outcome) {
    case "approved" -> new Approval(decisionId, id, employeeId, reason,
        approvedAmount, approvedTermMonths);
    case "refused" -> new Refusal(decisionId, id, employeeId, reason);
    case null, default -> throw new IllegalArgumentException(
        "Допустимы только одобрение и отказ");
};
```

Интерфейс CompletenessRule задаёт общий метод inspect. RequiredField находит отсутствующее поле, а RequiredDocument по ссылкам заявки ищет действующий документ нужного вида. В CompletenessCheck передаётся List<CompletenessRule>, поэтому алгоритм обходит правила через общий интерфейс. Документы хранятся в Map по идентификатору, заявки и связи представлены типами предметной модели, последовательности доходов и обязательств — списками, а набор конечных статусов — множеством Set. Массив String[] используется в стандартной точке входа Java для аргументов командной строки.

Фрагмент 3.2 — Вызов разных проверок через интерфейс и накопление результатов

```java
for (CompletenessRule rule : rules) {
    rule.inspect(input).ifPresent(missing -> {
        switch (missing.category()) {
            case FIELD -> missingFields.add(missing.name());
            case DOCUMENT -> missingDocuments.add(missing.name());
        }
    });
}
```

Для f проверяемых полей, r видов документов и d связей в худшей ветви циклов достигается O(f + r·d) при среднем O(1) доступе к словарю. Если встречаются коллизии хешей, итог зависит и от стоимости доступа, как показано в разделе 2.3. Расчёт нагрузки делает два независимых прохода, поэтому его время O(n + m) и дополнительная память O(1), где n и m — числа записей о доходах и обязательствах соответственно. Обе версии при отсутствии подтверждённого положительного дохода возвращают признак недостаточных сведений без значения процента.

| Ошибки | ValueError, например при отрицательном платеже | IllegalArgumentException, сообщение и ненулевой код выхода | Правило проверки сохранено. Main оформляет ошибку для командной строки |
| Новое правило | Проверку формата контакта можно добавить в check_request() или в вызывающий код | Новая реализация CompletenessRule и одна запись при сборке списка правил | Существующие реализации проверок сохраняются при расширении списка |

В Python основная программа занимает 212 строк в одном файле и содержит 6 функций. Java-реализация содержит 501 строку в 20 файлах исходников, каждый с отдельным типом верхнего уровня. Подсчёт включает пустые строки и комментарии, исключает инструкции, данные и конфигурацию сборки. Код стал объёмнее из-за явного преобразования JSON, деклараций типов и разнесения правил по классам. Проверку каждой ветви решения можно читать отдельно, однако для понимания полного сценария приходится переходить между классами.

Статическая типизация Java требует указывать типы полей, параметров и возвращаемых значений. В Python перестроить словарь или добавить поле можно непосредственно при обработке, а согласованность ключей и типов проверяется во время выполнения. Это различие связано с языком. Перенос проверок в наследников Decision и применение общего интерфейса для независимых правил связаны с организацией программы в ООП. Например, чтобы добавить проверку допустимого формата контакта, достаточно подключить новое правило при построении списка. Алгоритм сбора результатов и существующие проверки сохраняются. В Python ту же точку расширения можно создать списком функций. Текущая процедурная версия выполняет проверки непосредственно внутри check_request().

Входной пример одинаков в двух версиях. В заявке есть действительные документы, подтверждённый доход составляет 80 000 руб., действующие месячные платежи — 12 000 руб., предложенный платёж — 18 000 руб. В обеих версиях complete имеет значение true, payment_share_percent равен 37,5 %, итог approved указан сотрудником, sent имеет значение true. Сопоставление проведено на 19 сценариях, включая пробельное ФИО, неполный набор документов, отсутствие подтверждённого дохода, отказ и неудачную доставку. Для сценариев с результатом совпали значения JSON, для сценариев с аварийным завершением по входным данным — причины ошибки. При пробельном ФИО обе версии добавляют applicant.full_name в missing_fields и возвращают следующий шаг request_information. Две дополнительные проверки показали, что при отсутствии monthly_amount или monthly_payment Java печатает имя поля и идентификатор записи и завершает работу с кодом 1.

Первый приоритет — SQL и PostgreSQL. SQL требуется или указан в семи из десяти объявлений. В проекте уже есть ER-модель, поэтому следующий практический шаг — перенести её в PostgreSQL и отработать запросы по заявкам, решениям и попыткам уведомления.

Второй приоритет — прикладная разработка на Java и Spring Boot. Java указана в шести объявлениях, Spring фигурирует в описаниях всех четырёх ролей разработчика. Для портфолио можно перенести консольный сценарий в небольшой сервис с валидацией входных данных и контрактом API.

Третий приоритет — проектирование API и документирование требований. API и интеграционные контракты упоминаются в пяти объявлениях. Для практики стоит оформить спецификацию операций по заявке, описать коды ошибок и сопоставить методы со статусами BPMN.

Четвёртый приоритет — воспроизводимые автотесты. В четырёх объявлениях требуется опыт модульных проверок или разработки автотестов. Дальнейшая работа по проекту может начаться с тестов JUnit для границ расчёта и повторного уведомления, затем добавить запуск проверок при сборке.
