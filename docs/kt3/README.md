# КТ3. Реализация на Java и организационный раздел

Прототип КТ3 повторяет обработку одной учебной заявки из КТ2. За основу взяты [логическая модель](../../models/er_logical.drawio), [таблица операций](../kt2/report_section.md) и [процедурная реализация](../../src/main.py).

| Сущность КТ2 | Тип в Java | Связь |
|---|---|---|
| Заявитель | `Applicant` | Одна запись на заявителя, идентификатор используется в заявках, доходах и обязательствах |
| Заявка | `Application` | Принадлежит одному заявителю |
| Документ | `Document` | Может относиться к нескольким заявкам |
| ДокументЗаявки | `ApplicationDocument` | Связывает одну заявку и один документ, хранит дату получения |
| Согласие | `Consent` | Относится к одной заявке |
| РезультатПроверки | `CheckResult` | Относится к одной заявке |
| Доход | `Income` | Относится к одному заявителю |
| Обязательство | `Obligation` | Относится к одному заявителю |
| Решение | `Decision`, `Approval`, `Refusal` | У заявки может быть одно итоговое решение. При одобрении фиксируются сумма и срок, при отказе обязательно основание |
| Уведомление | `Notification` | Отдельная попытка доставки решения |

Связи передаются через идентификаторы из JSON КТ2. Денежные суммы представлены `BigDecimal`. Поля, которые алгоритм должен проверить на отсутствие значения, допускают `null`.

## Материал для сравнения реализаций

Исходник UML и его PNG находятся в [models/classes.puml](../../models/classes.puml) и [models/classes.png](../../models/classes.png). На диаграмме показаны предметные классы, правила и зависимости между ними. `ReviewWorkflow` создаёт и хранит свой экземпляр `CompletenessCheck` и `PaymentLoadCalculator`. Кратности предметных связей соответствуют логической модели КТ2. Команды сборки и запуска приведены в [README Java](../../src/java/README.md).

| Элемент | Python | Java | Причина изменения |
|---|---|---|---|
| Сущности | Словари с ключами из JSON | `Applicant`, `Application`, `Document` и другие типы с закрытыми полями | Типы фиксируют состав данных. Jackson преобразует JSON на границе программы |
| Проверка комплектности | `check_request()` и вложенный проход по связям документов | `CompletenessCheck.check()` вызывает `RequiredField.inspect()` и `RequiredDocument.inspect()` через `CompletenessRule` | Назначение каждого правила вынесено в отдельный тип. Сохраняется вложенный просмотр связей для каждого вида документа |
| Расчёт нагрузки | `calculate_payment_load()` суммирует доходы и обязательства за два прохода | `PaymentLoadCalculator.calculate()` выполняет те же два прохода по `List<Income>` и `List<Obligation>` | Сохраняется время `O(n + m)`, а аргументы явно описывают входные данные |
| Регистрация решения | `record_decision()` проверяет исход и обновляет копию словаря | `Application.recordDecision()` возвращает обновлённую заявку и объект `Approval` или `Refusal` | Одобрение проверяет сумму и срок, отказ проверяет основание. Правила соответствуют своим типам решений |
| Регистрация уведомления | `record_notification()` возвращает словарь попытки | `Decision.recordNotification()` возвращает `Notification` | Метод использует идентификатор решения, которому принадлежит попытка |
| Ошибки | `ValueError` для неправильного платежа или решения | `IllegalArgumentException`, сообщение в консоли и ненулевой код выхода | Проверки предметных правил сохранены. Обработка ошибки при запуске находится в `Main` |
| Новая проверка | Добавление нового вида проверки потребует расширить `check_request()` или изменить её вызов | Например, проверку формата контакта можно добавить реализацией `CompletenessRule` и её подключением при составлении списка правил | Контракт интерфейса позволяет сохранить циклы существующих правил |

Основная версия Python состоит из 6 функций в одном файле на 211 строк. Версия Java содержит 20 файлов исходников, около 490 строк и 20 типов верхнего уровня. Типы параметров, полей и результатов связаны со статической типизацией Java. Размещение валидации одобрения и отказа в наследниках `Decision`, а правил комплектности в реализациях интерфейса относится к организации поведения в ООП. Для простого случая это добавляет код, особенно для разбора и записи JSON, но помогает изолировать независимые правила.

В контрольном примере из КТ2 обе версии вернули `complete: true`, нагрузку 37,5 %, `outcome: approved` и `sent: true`. При сравнении 18 сценариев совпали значения в JSON для успешных запусков и причины отказа запуска для некорректных входных данных. Среди сценариев были отказ сотрудника, нехватка документов и дохода, а также неудачная доставка уведомления.
