# Рабочая аналитическая модель КТ2

## Граница и участники

Начальное событие — поступление заполненного обращения клиента. Конец — заявитель получил решение, а факт уведомления сохранён, либо заявка закрыта после отзыва или истечения срока предоставления недостающих сведений. Это границы раздела 1.5 КТ1. Дорожки МКК: кредитный специалист и уполномоченный сотрудник. Внешние участники: заявитель, БКИ и сервис уведомлений. Последние два не принимают кредитное решение.

Последовательность для BPMN: зарегистрировать заявку → проверить комплектность → при нехватке сведений запросить уточнение и вернуться к проверке после получения данных либо закрыть заявку с основанием при отзыве или истечении срока → проверить личность и согласия → проверить ограничения → получить внешние сведения при наличии основания → рассчитать предварительную платёжную нагрузку → подготовить предложение → уполномоченный сотрудник принимает решение → зафиксировать решение по заявке → направить и подтвердить уведомление. Ошибка внешнего сервиса ведёт в ожидание, а не в успешную проверку. Отказ, одобрение и закрытие без решения различаются.

Объекты данных BPMN: анкета заявителя, заявка, документ, согласие, результат проверки, предложение, решение, уведомление. У каждого объекта есть соответствующая сущность или атрибут в логической модели ниже.

## Автоматизируемые операции

Названия в первом столбце должны дословно повторяться в задачах BPMN.

| № | Операция на BPMN | Сейчас выполняет | Что делает программа | Функция |
|---|---|---|---|---|
| 1 | Проверить комплектность заявки | Кредитный специалист вручную сверяет анкету и документы | Выдаёт перечень пустых полей и отсутствующих действительных документов | `check_request()` |
| 2 | Рассчитать предварительную платёжную нагрузку | Кредитный специалист суммирует подтверждённые доходы и действующие платежи | Рассчитывает учебную долю платежей и сообщает о недостатке данных | `calculate_payment_load()` |
| 3 | Зафиксировать решение по заявке | Уполномоченный сотрудник оформляет результат | Проверяет допустимость записи, сохраняет исход и основание | `record_decision()` |
| 4 | Зафиксировать уведомление заявителя | Кредитный специалист фиксирует отправку | Записывает канал и результат попытки уведомления | `record_notification()` |

Программа **не принимает решение автоматически**. Расчёт нагрузки в прототипе не объявляется нормативным расчётом ПДН: такой расчёт требует уточнения действующей методики, состава доходов и обязательств. Решение вводит уполномоченный сотрудник.

## Логические сущности

Типы SQL и индексы здесь не определяются: это физическая модель КТ4.

| Сущность | Назначение | Атрибуты, помимо ключей | Ключи |
|---|---|---|---|
| Заявитель | Лицо, подавшее обращение | ФИО, контакт | `applicant_id` — PK |
| Заявка | Экземпляр процесса | Сумма, срок, статус, дата поступления | `application_id` — PK; `applicant_id` — FK |
| Документ | Предоставленный документ | Вид, признак действительности | `document_id` — PK |
| ДокументЗаявки | Связь документа и заявки, дата получения | Дата получения | (`application_id`, `document_id`) — составной PK и два FK |
| Согласие | Основание запроса внешних сведений | Вид, дата, статус | `consent_id` — PK; `application_id` — FK |
| РезультатПроверки | Итог проверки личности, ограничений или БКИ | Вид, источник, дата, результат | `check_id` — PK; `application_id` — FK |
| Доход | Подтверждённое сведение для предварительного расчёта | Месячная сумма, подтверждение | `income_id` — PK; `applicant_id` — FK |
| Обязательство | Действующий платёж для расчёта | Месячный платёж, активность | `obligation_id` — PK; `applicant_id` — FK |
| Решение | Принятый сотрудником исход | Исход, причина, согласованные параметры, дата, сотрудник | `decision_id` — PK; `application_id` — FK |
| Уведомление | Попытка доведения результата | Канал, дата, статус передачи | `notification_id` — PK; `decision_id` — FK |

Один заявитель может подать много заявок; каждая заявка принадлежит одному заявителю (1:N). Заявка связана с несколькими документами, документ может подтверждать несколько обращений того же заявителя: M:N разрешена сущностью `ДокументЗаявки` с двумя связями 1:N. У заявки может быть много согласий и результатов проверок (1:N). Один заявитель может иметь несколько записей дохода и обязательства (1:N). У заявки может быть не более одного итогового решения (1:0..1); у решения — несколько попыток уведомления (1:N).

Первая нормальная форма: атрибуты атомарны, список документов не записывается в одну ячейку заявки. Вторая: атрибут `received_at` в `ДокументЗаявки` зависит от всей пары ключей; свойства документа хранятся отдельно и зависят только от `document_id`. Третья: контакт заявителя зависит от `applicant_id`, а не от номера заявки; сведения о документе и решении также вынесены в отдельные сущности. Если повторять контакт и сведения документа в каждой заявке, их изменение приводило бы к противоречиям.

## Алгоритмы и оценки

**1. Проверить комплектность заявки.** Пусть `f` — число обязательных полей, `r` — число требуемых видов документов, `d` — число связей заявки с документами, `k` — число документов в словаре. Для каждого поля выполняется одна проверка; для каждого вида документа просматриваются связи, пока не найден действительный документ. В худшей ветви циклов при обычном среднем `O(1)` доступе к словарю время `O(f + r·d)`, дополнительная память `O(f + r)` для перечня недостающего. Теоретическая верхняя оценка с патологическими коллизиями хешей — `O(f + r·d·k)`. В алгоритме есть ветвление и вложенный цикл. Его задача на BPMN и функция в коде называются соответственно «Проверить комплектность заявки» и `check_request()`.

**2. Рассчитать предварительную платёжную нагрузку.** Пусть `n` — число записей дохода и `m` — число обязательств заявителя. Каждый список просматривается один раз, поэтому время `O(n + m)`, дополнительная память `O(1)`. Если подтверждённого дохода нет, результатом становится сообщение о недостатке данных, а не нулевая нагрузка. Для остальных случаев вычисляется `(действующие месячные платежи + предложенный платёж) / подтверждённый месячный доход`. Внешняя сортировка или поиск не применяются. Это учебная предварительная оценка, не основание автоматического одобрения или отказа.

Блок-схемы должны показывать проверки, циклы и выходы этих функций. После создания схемы следует сверить каждую ветвь с кодом.
