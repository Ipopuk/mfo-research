## 1.6 Среда разработки и система контроля версий


Выбор инструментов учитывает учебный план практики: сначала предусматривается процедурная реализация алгоритмов на Python, затем объектно-ориентированная реализация на Java и физическая модель данных в СУБД. На КТ1 подготовлены структура проекта, текстовые материалы исследования, рекомендации расширений редактора и служебные сценарии. Реализация кредитного процесса и схема базы данных относятся к следующим этапам.

В качестве общей среды разработки выбрана Visual Studio Code версии 1.95 или новее. Редактор поддерживает работу с файлами исследования и Git, а расширения позволяют использовать Python и Java в одном рабочем пространстве. В отличие от выбора отдельной IDE для каждого языка такой вариант упрощает освоение единого набора операций. В комплект включён список рекомендуемых расширений: Python, Pylance и Extension Pack for Java. Возможности базовой версии среды описаны в официальных материалах Microsoft [14].

Для процедурной реализации выбрана ветка Python 3.13. Язык позволяет компактно записать последовательность проверок и преобразование данных, а стандартная библиотека — подготовить служебные сценарии без большого набора зависимостей. В отличие от немедленного использования Java на всех этапах этот выбор соответствует требованию процедурной реализации. При работе с денежными величинами предусматривается десятичное представление и явно заданное округление. Документация выбранной ветки опубликована Python Software Foundation [15].

Для объектно-ориентированной реализации выбран Java 21 с комплектом разработки JDK. Статическая типизация и классы позволяют описать заявку, результат проверки и решение как самостоятельные объекты. Тип BigDecimal и средства управления округлением подходят для денежных расчётов. Java используется на следующем этапе после подготовки алгоритмов на Python, что позволит сопоставить две реализации на одинаковых сценариях [16].

Для хранения данных выбрана PostgreSQL 17. Реляционная СУБД поддерживает ограничения целостности и транзакции, необходимые при изменении статуса заявки и сохранении решения. Тип numeric позволяет хранить десятичные значения. По сравнению с файловой SQLite выбранная СУБД лучше соответствует будущей работе нескольких сотрудников с общей базой. Окончательная структура таблиц будет разработана после логической модели данных [17].

Система контроля версий — Git версии 2.47 или новее; для удалённого размещения предполагается GitHub. Git сохраняет последовательность изменений, позволяет сравнивать текстовые версии исследования и продолжать работу локально. В отличие от папок с копиями файлов история связывает каждое изменение с конкретным сообщением и автором. GitHub выбран для размещения репозитория и получения устойчивой ссылки на проект [18].

Базовые ветки Python, Java и PostgreSQL фиксируются для воспроизводимости учебной работы. При установке следует использовать актуальные исправляющие выпуски внутри выбранных веток, а не обязательно первоначальные версии. Для проверки среды используются команды python --version, java --version, javac --version, psql --version, code --version и git --version. Служебный сценарий tools/check_environment.py сохраняет фактические версии и сообщает о недоступных инструментах. Наличие клиента psql подтверждает его установку, но само по себе не подтверждает запуск сервера базы данных.

В репозитории подготовлены README.md с темой и полем ФИО, .gitignore, текстовые разделы исследования, список источников в формате BibTeX, материалы перевода и отчёт. Текстовые версии в Markdown позволяют видеть содержательные изменения в Git, тогда как файл DOCX удобен для сдачи. В .gitignore исключены временные файлы редактора, виртуальная среда, результаты сборки и локальные параметры с секретами.

Работу следует фиксировать отдельными осмысленными коммитами: создание описания проекта; добавление анализа предметной области и источников; описание бизнес-процесса; добавление оригинала и перевода; оформление отчёта и средств проверки. Время коммитов и сведения об авторе должны соответствовать фактической истории. Подтверждение работы с Git составляют существующий удалённый репозиторий и выгрузка его истории, а не заранее написанный перечень предполагаемых изменений.

После создания личного репозитория его адрес записывается одной строкой в vcs/repo_url.txt. История выгружается командой git log --all --date=iso --pretty=format:"%h %ad %an %s" и сохраняется в vcs/git_log.txt. Эти файлы формируются из фактического репозитория при сборке архива. Требование КТ1 о трёх коммитах в разные дни проверяется отдельно; подготовленные материалы и изменение метаданных Git не подтверждают его выполнения.
