## Рецензия на работу одногруппника

Автор — Лимонов Никита Алексеевич, ИКБО-10-24. Проект посвящён оформлению индивидуальных заказов на пошив. [Репозиторий](https://github.com/NikitLim/individual-sewing-orders). Проверена [версия `9cf6dd255ebe59e6ae0a9bc70efde2577eb1a851`](https://github.com/NikitLim/individual-sewing-orders/tree/9cf6dd255ebe59e6ae0a9bc70efde2577eb1a851).

Сверены UML и исходники, связи и кратности, наследование `OrderLine`, две реализации интерфейса `OrderCheck`, применение `List` и `Set` и читаемость загрузки TSV. Сборка по README с `javac --release 21` прошла. Контрольный заказ 1001 дал 8 850 ₽ за материалы, 7 900 ₽ за работы и итог 16 750 ₽. Проверки комплектности и остатков выполнены, сформировано задание № 1. Пограничные примеры запускались на отдельных копиях демонстрационных TSV.

### 1. Остаток материала проверяется отдельно для каждой строки заказа

[`src/java/OrderCheck.java:43–61`](https://github.com/NikitLim/individual-sewing-orders/blob/9cf6dd255ebe59e6ae0a9bc70efde2577eb1a851/src/java/OrderCheck.java#L43-L61), метод `MaterialAvailabilityCheck.check`. При запасе 12 м и наличии строки на 3 м я добавила вторую строку на 10 м для того же материала в заказе 1001. Программа напечатала «Материалы: ОК» и сформировала задание, хотя требуется 13 м. Предлагаю суммировать количество по `materialId` с помощью `Map<Long, BigDecimal>`, затем сравнивать совокупный расход с доступным остатком.

### 2. Задание выдаётся с истёкшим сроком готовности

[`src/java/OrderService.java:23–40`](https://github.com/NikitLim/individual-sewing-orders/blob/9cf6dd255ebe59e6ae0a9bc70efde2577eb1a851/src/java/OrderService.java#L23-L40), метод `evaluate`. Для согласованного заказа со сроком 01.11.2026 программа сформировала задание с датой выдачи 24.11.2026. Предлагаю один раз вычислить дату по переданному `Clock`, проверить `dueDate.isBefore(issuedAt)` перед созданием задания и вернуть понятную причину отказа. Отдельно стоит проверить срок, совпадающий с датой выдачи.

### 3. Чтение TSV пропускает проверку имён и порядка столбцов

[`src/java/OrderData.java:30–36, 41–57`](https://github.com/NikitLim/individual-sewing-orders/blob/9cf6dd255ebe59e6ae0a9bc70efde2577eb1a851/src/java/OrderData.java#L30-L57), методы `load`. При перестановке `customer_id` и `model_id` в заголовке `orders.tsv` программа продолжила принимать файл. Эти поля одного типа, поэтому при перестановке реальных столбцов перепутанные ссылки могут пройти проверку. Предлагаю сравнивать первую строку с ожидаемыми названиями и порядком полей. При несовпадении выводить имя таблицы и ожидаемую схему.

### UML и организация кода

Иерархия Decision → Approval / Refusal соответствует исходникам. Одобрение требует положительной суммы и срока, а отказ требует основания. Интерфейс CompletenessRule действительно используется полиморфно: CompletenessCheck обходит List<CompletenessRule> и вызывает inspect у правил RequiredField и RequiredDocument.

Выбор коллекций соответствует операциям. Map позволяет найти документ по идентификатору, List хранит связи и сохраняет порядок проверок, Set используется для проверки конечных статусов. ReviewWorkflow создаёт и хранит оба сервиса проверки, как показано композицией на UML. Предметные записи и методы имеют понятные имена. Чтение JSON вынесено в JsonCases, поэтому последовательность обработки можно проследить в ReviewWorkflow.review без разбора формата файла.

### Замечания

1. **Обязательное ФИО проходит проверку, если состоит из пробелов.** В примере заменил только applicant.full_name на три пробела. Получил complete=true и approved. В RequiredField.inspect сравнение с пустой строкой пропускает пробельный текст. Предлагаю для значения типа String применять isBlank() и добавить проверку: пробельное ФИО попадает в missing_fields, следующий шаг — request_information. [RequiredField.java, строки 8–11](https://github.com/Ipopuk/mfo-research/blob/8357f55/src/java/src/main/java/mfo/kt3/RequiredField.java#L8-L11)

2. **Отсутствующая сумма подтверждённого дохода прерывает расчёт с NullPointerException.** Удалил monthly_amount у подтверждённого дохода заявителя. Программа завершилась с кодом 1 и трассировкой. JsonCases передаёт null при отсутствии числа, а калькулятор складывает это значение с накопителем. Та же предпосылка есть для monthly_payment активного обязательства. Предлагаю проверять обе суммы перед сложением и выдавать понятную ошибку с полем и идентификатором записи. Для обеих коллекций стоит добавить примеры с отсутствующей суммой. [JsonCases.java, строки 60–63](https://github.com/Ipopuk/mfo-research/blob/8357f55/src/java/src/main/java/mfo/kt3/JsonCases.java#L60-L63) · [PaymentLoadCalculator.java, строки 21–32](https://github.com/Ipopuk/mfo-research/blob/8357f55/src/java/src/main/java/mfo/kt3/PaymentLoadCalculator.java#L21-L32)

3. **На UML трудно различить два типа Input и два типа Result.** В сигнатурах CompletenessCheck.check и ReviewWorkflow.review указаны короткие имена. В коде у каждого класса собственные вложенные типы с разными полями. Предлагаю подписать их как CompletenessCheck.Input / Result и ReviewWorkflow.Input / Result и обновить PNG. Это сделает сигнатуры однозначными без добавления новых блоков на диаграмму. [classes.puml, строки 168–179](https://github.com/Ipopuk/mfo-research/blob/8357f55/models/classes.puml#L168-L179)
